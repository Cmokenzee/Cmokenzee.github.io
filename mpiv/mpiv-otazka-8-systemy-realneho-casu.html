01

Co je systém reálného času

Real-Time System (RTS) je systém, kde správnost výsledku závisí nejen na logické správnosti výpočtu, ale TAKÉ na čase, kdy je výsledek produkován. Nestačí vypočítat správný výsledek – musí být hotový DO DEADLINE!

Klíčový rozdíl od běžných systémů

Běžný systém: „Spočítej 2+2" → výsledek 4 je správný kdykoli.

RTS: „Spočítej 2+2 do 10 ms" → výsledek 4 po 11 ms je CHYBA!

Kde se RTS používá
  • Automotive – airbag musí vybuchnout do 20 ms po nárazu
  • Letectví – fly-by-wire, kontrola křídel každých 10 ms
  • Průmysl – robotické rameno, CNC stroje
  • Medicína – kardiostimulátor, infuzní pumpy
  • Telekomunikace – zpracování packetů, switching
  • Multimedia – audio/video streaming (16.7 ms @ 60 FPS)
Co NENÍ RTS

RTS ≠ „rychlý systém". RTS je o PŘEDVÍDATELNOSTI, ne jen o rychlosti. Supercomputer může být velmi rychlý (petaflops), ale NENÍ RTS, protože čas není garantovaný.

Hard Real-Time

Deadline MUSÍ být splněn. Nedodržení = katastrofa/selhání systému.

Příklady Hard RT
  • Airbag – musí vybuchnout do 20 ms. Po 30 ms je pozdě → smrt
  • ABS brzdy – kontrola každých 10 ms. Zpoždění → smyk, nehoda
  • Kardiostimulátor – stimulace musí být přesná. Zpoždění → úmrtí
  • Fly-by-wire – kontrola křídel každých 10 ms. Miss → pád
  • Nuclear reactor – monitoring každých 100 ms. Miss → meltdown

Vyžaduje: WCET (Worst-Case Execution Time) musí být známý, matematicky ověřitelné (schedulability analysis).

Firm Real-Time

Deadline by měl být splněn. Občasné nedodržení tolerovatelné, ale výsledek je pak BEZCENNÝ.

Příklady Firm RT
  • Video streaming – frame musí být ready každých 16.7 ms (60 FPS). Pozdní frame se skipne → občasné škubání OK
  • Voice over IP – packet po deadline zahozený. Občasný výpadek → crackling
  • Online gaming – input po deadline ignorován → hráč pocítí lag

Soft Real-Time

Deadline je žádoucí. Nedodržení snižuje kvalitu, ale výsledek je stále POUŽITELNÝ.

Příklady Soft RT
  • YouTube video – buffer může čekat, video se přehraje později
  • Webový server – stránka za 500 ms místo 100 ms. Pomalejší, ale funkční
  • Email notifikace – přijde o 5 sekund později. OK
  • UI refresh – displej updated každých 100 ms místo 50 ms. Méně responsivní
03

Úloha (Task) a její parametry

Task je jednotka práce, která má být vykonána. V RTS má task časové požadavky (deadline, perioda).

C Computation time Doba vykonání (WCET)
D Deadline Čas do kdy MUSÍ být hotový
T Period Jak často se opakuje
R Release time Kdy je task ready

Typy tasků

Periodický task

Opakuje se pravidelně každých T ms. Příklad: čtení teploty každou sekundu (T=1000, C=5, D=1000).

Aperiodický task

Objevuje se nepravidelně, nelze předpovědět kdy. Příklad: stisk tlačítka uživatelem.

Sporadický task

Jako aperiodický, ale s minimálním intervalem mezi výskyty. Příklad: interrupt handler (min. každých 10 ms).

04

Dávka (Job), Deadline, Laxita

Dávka (Job/Instance)

Job je JEDNO VYKONÁNÍ tasku. Periodický task generuje nekonečně mnoho jobů.

PERIODICKÝ TASK – JOBY
Task: „Čti teplotu každou sekundu"
Job 1 @ t=0 ms   │    Job 2 @ t=1000 ms   │    Job 3 @ t=2000 ms   │   ...

Deadline

Deadline je absolutní časový limit do kdy MUSÍ být job dokončen.

TypPodmínkaPopis
ImplicitD = TDeadline = perioda (nejčastější)
ConstrainedD ≤ TDeadline před dalším release
ArbitraryD > TMůže být i po dalším release
Příklad výpočtu deadline

Task: T=100 ms, D=100 ms (implicit)

Job 1 release: t=0 → deadline = 0+100 = 100 ms

Job 2 release: t=100 → deadline = 100+100 = 200 ms

Laxita (Slack Time)

Laxita je čas, o který lze zpozdit start tasku BEZ porušení deadline. Kolik „volného času" máme.

Laxita = (Deadline − Current_Time) − Remaining_Execution_Time
L = (D − t) − C_remaining
Praktický příklad laxity

Task: C=20 ms, D=100 ms, current time t=30 ms

Zbývající čas do deadline: 100 − 30 = 70 ms

Potřebný čas: 20 ms

Laxita: 70 − 20 = 50 ms → Task můžeme zdržet o 50 ms a stále stihneme deadline.

VIZUALIZACE LAXITY
t=30 (now) t=100 (deadline)
Laxita = 50 ms (volný čas)
C = 20 ms
Interpretace laxity
  • Laxita = 0 → task musí běžet TEĎ nebo miss deadline
  • Laxita > 0 → ještě můžeme čekat
  • Laxita < 0 → deadline už nemožné splnit!
  • Použití v Least Laxity First (LLF) scheduling
05

Statické plánování – Rate Monotonic

Statické plánování (offline): Schedule vytvoříme PŘED spuštěním systému. Tasky, časy a pořadí jsou známé dopředu. Schedule je pak fixní – neměnný za běhu.

VÝHODY

  • Předvídatelné – víme co kdy běží
  • Nízký overhead
  • Snadné testování
  • Vhodné pro certifikaci

NEVÝHODY

  • Nepružné – nelze reagovat na změny
  • Špatné pro aperiodické tasky
  • Neoptimální využití CPU

Rate Monotonic (RM)

Fixní priorita založená na periodě. Kratší perioda = vyšší priorita.

Priority(Task_i) = 1 / Period(Task_i)
Nejkratší perioda → nejvyšší priorita
Příklad RM plánování
TaskC (výpočet)T (perioda)Priorita
Task A2 ms5 ms1 (nejvyšší)
Task B3 ms10 ms2
Task C2 ms20 ms3 (nejnižší)
RM TIMELINE (ZJEDNODUŠENĚ)
0–2: A │ 2–5: B │ 5–7: A (preemptuje B) │ 7–9: C │ 9–10: B done │ 10–12: A │ ...

RM Schedulability Test

U = Σ(C_i / T_i) ≤ n × (2^(1/n) − 1)
Kde n = počet tasků. Pokud U pod limitem → všechny deadlines zaručeně splněny
Počet tasků (n)Max utilization

574.3%
∞69.3% (ln 2)
Příklad výpočtu utilization
// Task A: C=2, T=5; Task B: C=3, T=10; Task C: C=2, T=20
U = 2/5 + 3/10 + 2/20
U = 0.4 + 0.3 + 0.1 = 0.8 (80%)

06

Dynamické plánování – EDF, LLF

Dynamické plánování (online): Scheduling rozhodnutí děláme ZA BĚHU. Priority se mění dynamicky podle aktuální situace.

VÝHODY

  • Flexibilní – reaguje na změny
  • Lepší využití CPU
  • Zvládá aperiodické tasky

NEVÝHODY

  • Runtime overhead
  • Složitější analýza
  • Méně předvídatelné

Earliest Deadline First (EDF)

Dynamická priorita podle absolutního deadline. Nejbližší deadline = nejvyšší priorita.

Priority = Deadline (čím nižší číslo, tím vyšší priorita)
Příklad EDF

Task A: C=2, T=5, D=5  │  Task B: C=3, T=10, D=10

t=0: A.deadline=5, B.deadline=10 → běží A (bližší deadline)

t=2: A done → běží B

t=5: Nový A job, A.deadline=10, B.deadline=10 → stejné, pokračuje B...

EDF Schedulability Test

U = Σ(C_i / T_i) ≤ 1.0 (100%)
EDF je OPTIMÁLNÍ – pokud nějaký algoritmus dokáže schedule, EDF taky!
EDF je optimální!

RM max 69% utilization, EDF až 100% → EDF má výrazně lepší využití CPU. Pokud existuje schedule pro danou task sadu, EDF ho najde.

Least Laxity First (LLF)

Priorita podle laxity. Nejmenší laxita = nejvyšší priorita = nejnaléhavější.

Laxita = (Deadline − Current_Time) − Remaining_Time
Nejmenší laxita → nejdříve běží
LLF vlastnosti
  • Výhoda: detekuje deadline miss DŘÍVE než EDF
  • Nevýhoda: více context switches (častěji přepočítává priority)
  • Také optimální (jako EDF) pro preemptivní systémy

Kdy co použít?

RM – certifikované systémy (automotive, letectví), jednoduché, předvídatelné, low overhead.

EDF – maximální využití CPU, flexibilní systémy, když RM nestačí (U > 69%).

08

Spolehlivost – pojmy a metriky

Reliability (spolehlivost) = pravděpodobnost, že systém bude fungovat správně po určitou dobu za daných podmínek.

Klíčové pojmy
  • Failure (selhání) – systém neposkytuje správnou službu
  • Fault (porucha) – příčina selhání (HW defekt, SW bug)
  • Error (chyba) – část systému ve špatném stavu

Typy poruch

Permanent Fault

Trvalá porucha, trvá dokud se fyzicky neopraví. Příklad: spálený transistor, přeražený vodič.

Transient Fault

Dočasná, sama zmizí. Příklad: kosmické záření (bit flip v RAM), EMI interference.

Intermittent Fault

Objevuje se a mizí nepředvídatelně. Příklad: špatné spojení (cold solder joint), přehřívání.

Metriky spolehlivosti

MetrikaVýznamPříklad
MTTFMean Time To Failure – průměrná doba do první poruchy (neopravitelné systémy)LED: MTTF = 50 000 h
MTTRMean Time To Repair – průměrná doba opravyServer: MTTR = 4 h
MTBFMean Time Between Failures – pro opravitelné systémy. MTBF = MTTF + MTTR
Availability = MTTF / (MTTF + MTTR) = MTTF / MTBF
Příklad: MTTF=1000 h, MTTR=10 h → A = 1000/1010 = 99%
09

Hardwarová a informační redundance

Redundance = přidání extra komponent/dat pro toleranci chyb. Hlavní technika odolnosti proti poruchám.

A) Hardware Redundance

DMR (Dual Modular)

2 stejné moduly, porovnání výstupů. Neshodují se → error detected. Příklad: dva senzory teploty, rozdíl >5°C → alarm.

TMR (Triple Modular)

3 stejné moduly + majority voter. 2 ze 3 musí souhlasit. Toleruje JEDNU chybu. Letectví, spacecraft.

B) Informační redundance

Extra bity pro detekci/korekci chyb v datech.

MetodaSchopnostPoužití
Parity bitDetekuje lichý počet chyb, NEKORRIGUJEUART komunikace
CRC (Cyclic Redundancy Check)Detekuje burst errors. CRC-8/16/32Ethernet, UART, CAN
ECC (Error Correcting Code)Detekuje A OPRAVÍ chyby (SECDED)ECC RAM, Flash memory
SECDED

Single Error Correct, Double Error Detect – Hamming code. Opraví 1-bit chybu, detekuje 2-bit chybu. Standardní v ECC RAM.

C) Časová redundance

Opakování operace. Pokud transient fault → druhý pokus uspěje.

Příklad

Přečti ADC 3× a udělej median. Noise spike ignorován. Jednoduché a efektivní proti transient faults.

10

Watchdog, Checkpointing, Degradace

Watchdog Timer

Hardware timer, který musí být periodicky resetován softwarem. Pokud SW zamrzne → watchdog vyvolá reset.

Princip Watchdogu
1
Watchdog timer běží kontinuálně
2
SW musí „kicknout" watchdog každých X ms
3
Pokud timeout → systém RESET
SW zamrzl → watchdog zachrání systém automatickým restartem
Příklad kódu (AVR Watchdog)
wdt_enable(WDTO_1S); // Enable 1 second watchdog

while(1) {
  do_work();
  wdt_reset(); // Kick watchdog – jsem naživu!
}

Checkpointing

Periodicky uložit stav systému. Po selhání → obnova z posledního checkpointu.

Příklad

Databáze každých 10 min uloží transaction log. Crash → rollback k poslednímu uloženému stavu. Ztráta max 10 min dat.

Graceful Degradation

Systém pokračuje v omezeném režimu místo úplného selhání.

Příklad: Auto

ABS selhání → deaktivuj ABS, ale brzdění stále funguje manuálně.

Příklad: Dron

GPS selhání → přepni na barometric altitude hold. Omezená navigace, ale bezpečný let.

Fail-Safe vs Fail-Operational

Fail-Safe

Při selhání přejdi do BEZPEČNÉHO stavu (vypni, zastav). Příklad: výtah – porucha → brzdy aktivují, výtah zastaví.

Fail-Operational

Při selhání POKRAČUJ v provozu (redundance to umožní). Příklad: letadlo – jeden engine fail → létá na druhém.

Self-Healing

Systém automaticky detekuje a opravuje chyby.

Příklady
  • Flash memory – wear leveling přesouvá data z opotřebených bloků
  • RAID – disk failure → automatická rebuild z parity dat
11

Shrnutí klíčových bodů

Na zkoušku si zapamatuj

SYSTÉM REÁLNÉHO ČASU

  • Správnost = logika + ČAS. Výsledek po deadline = CHYBA
  • RTS ≠ rychlý systém. RTS = předvídatelný systém
  • Hard RT – miss = katastrofa (airbag, ABS, kardiostimulátor)
  • Firm RT – miss = zahoď výsledek (video frame, VoIP packet)
  • Soft RT – miss = degradace (YouTube lag, web latency)

ZÁKLADNÍ POJMY

  • Task – jednotka práce (C = výpočet, D = deadline, T = perioda, R = release)
  • Job – jedno vykonání tasku (instance)
  • Deadline typy: implicit (D=T), constrained (D≤T), arbitrary (D>T)
  • Laxita: L = (D − t) − C_remaining. L=0 → teď! L<0 → nemožné

PLÁNOVÁNÍ

  • Statické (RM): fixní priorita, kratší perioda = vyšší. Max U ≤ 69%. Certifikace
  • Dynamické (EDF): bližší deadline = vyšší priorita. Optimální, U ≤ 100%
  • LLF: nejmenší laxita = nejvyšší priorita. Optimální, více context switches

SPOLEHLIVOST

  • Fault typy: permanent (trvalá), transient (dočasná), intermittent (občasná)
  • Metriky: MTTF (do poruchy), MTTR (oprava), MTBF = MTTF + MTTR
  • Availability = MTTF / MTBF

ODOLNOST PROTI PORUCHÁM

  • HW redundance: DMR (detekce), TMR (korekce – 2 ze 3 voter)
  • Info redundance: Parity (detekce), CRC (burst), ECC/SECDED (korekce)
  • Time redundance: opakování (median filter z 3 čtení)
  • Watchdog timer – detekuje freeze, automatický reset
  • Checkpointing – uložení stavu, rollback po selhání
  • Graceful degradation – omezený režim místo crash
  • Fail-safe (bezpečný stav) vs Fail-operational (pokračování s redundancí)
Zlatá pravidla
  • RTS: čas je ČÁST správnosti! Nejde jen o rychlost, jde o garance
  • EDF je optimální (100%), RM jednodušší (69%) – vhodný pro certifikaci
  • TMR toleruje 1 chybu (2 ze 3 voter). Letectví, vesmír
  • Watchdog zachrání freeze. Vždy používat v embedded!
  • Redundance = cesta k spolehlivosti na všech úrovních (HW, data, čas)
