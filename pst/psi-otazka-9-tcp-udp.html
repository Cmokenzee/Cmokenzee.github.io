01

Transportní vrstva (L4)

Transportní vrstva poskytuje end-to-end komunikaci mezi aplikacemi. Hlavní funkce: segmentace, multiplexování (porty), error detection, flow control, connection management.

TCP Spolehlivý

Connection-oriented. Garantované doručení, správné pořadí, flow control. HTTP, FTP, SSH, Email.

UDP Rychlý

Connectionless. Žádné ACK, žádné retransmission. Minimální overhead. DNS, VoIP, streaming, gaming.

02

Přepínání obvodů vs. datagramů

Circuit Switching (obvodů)

Pevná cesta vytvořena PŘED přenosem. Rezervovaný bandwidth po celou dobu spojení. Konstantní delay. Příklad: telefonie (PSTN). Nevýhoda: plýtvání (i při mlčení).

Packet Switching (datagramů)

Data rozdělena na pakety, každý směrován nezávisle. Sdílený bandwidth. Variable delay. Příklad: Internet (TCP/IP). Efektivní, škálovatelné, robustní.

TCP/IP používá packet switching. IP (L3) je nespolehlivý (best effort). TCP (L4) přidává spolehlivost NAD nespolehlivý IP.

03

TCP – přehled a vlastnosti

Klíčové vlastnosti TCP
  • Connection-oriented – spojení navázáno PŘED přenosem (3-way handshake)
  • Reliable – garantované doručení (ACK, retransmission)
  • Ordered delivery – data v původním pořadí (sequence numbers)
  • Flow control – řízení rychlosti (sliding window)
  • Congestion control – detekce přetížení sítě (slow start, congestion avoidance)
  • Full-duplex – data oběma směry současně
  • Byte-stream oriented – TCP vidí data jako proud bytů (ne zprávy)

Použití: HTTP, HTTPS, FTP, SSH, SMTP, POP3, IMAP – vše co vyžaduje spolehlivost.

Klíčová pole
  • Source / Destination Port (16 b) – identifikace aplikací
  • Sequence Number (32 b) – číslo prvního byte dat v segmentu
  • Acknowledgment Number (32 b) – číslo dalšího očekávaného byte

  • Checksum (16 b) – error detection (header + data)
  • Options (0–40 B) – MSS, Window Scale, SACK, Timestamps
05

Segmentace a multiplexování

Segmentace

Aplikace pošle data → TCP rozdělí na segmenty. Důvod: MTU limit (Ethernet MTU = 1500 B).

MSS (Maximum Segment Size)

MSS = MTU − IP header − TCP header = 1500 − 20 − 20 = 1460 B

MSS vyjednán během 3-way handshake (TCP Options). Každá strana oznamuje své MSS.

Multiplexování (Porty)

Port numbers (16 bit, 0–65535) identifikují aplikace na jednom zařízení.

RozsahNázevPříklady
0–1023Well-knownHTTP 80, HTTPS 443, SSH 22, FTP 21, DNS 53, SMTP 25
1024–49151RegisteredMySQL 3306, RDP 3389, PostgreSQL 5432
49152–65535Dynamic / EphemeralDočasné porty (klient při navazování spojení)
Socket a spojení

Socket = IP adresa : Port (např. 192.168.1.5:443)

TCP spojení = 4-tuple: Source IP + Source Port + Dest IP + Dest Port (unikátně identifikuje spojení)

Proč 3-way (ne 2-way)?
  • Synchronizace ISN – obě strany znají ISN partnera
  • Ověření partnera – prevence starých duplicitních SYN
  • Prevence SYN flood – server potvrdí až po obdržení finálního ACK
07

Ukončení spojení – 4-way handshake

Čtyři fáze ukončení
1
FIN → (Klient → Server)
FIN=1, SEQ=3000. „Ukončuji odesílání dat."
2
ACK ← (Server → Klient)
ACK#=3001. „Rozumím. Ale já můžu ještě posílat!" (half-close)
3
FIN ← (Server → Klient)
FIN=1, SEQ=7000. „Teď i já končím."
4
ACK → (Klient → Server)
ACK#=7001. „OK, ukončeno!" → TIME_WAIT → CLOSED
Proč 4-way (ne 2-way)?

Full-duplex → každý směr ukončen samostatně. Half-close možný (klient FIN → server stále posílá → server FIN).

TIME_WAIT: 2×MSL (typicky 4 min) po finálním ACK. Pokud finální ACK ztracen → server re-transmit FIN → klient musí odpovědět. Zajistí expiraci starých segmentů.

08

Řízení toku – Sliding Window

Problém

Odesílatel může vysílat rychleji než příjemce zpracovává → buffer overflow!

Řešení: Plovoucí okno (Sliding Window)

Příjemce má receive buffer. V ACK posílá Window Size = kolik bytů může odesílatel poslat BEZ čekání na další ACK.

  • Aplikace čte data → buffer se uvolňuje → Window roste
  • Buffer plný → Window = 0 → odesílatel MUSÍ čekat!
  • Okno „pluje" dopředu s každým ACK

Příklad: Window = 4 KB, SEQ start = 1000

ACKed ✓
← Okno (lze poslat) →
Čeká (mimo okno)
Window Size 0 a Persist Timer

Buffer plný → Window=0 → odesílatel nesmí posílat data. Persist Timer: odesílatel periodicky posílá Window Probe (1 B) → příjemce odpoví aktuálním Window. Zabraňuje deadlocku (oba čekají).

Window Scale Option (RFC 1323)

Window Size = 16 bitů → max 65535 B (64 KB) → málo pro Gigabit sítě!

Window Scale: faktor 0–14 → Window × 2scale. Max: 65535 × 214 ≈ 1 GB! Vyjednán při handshake.

09

Spolehlivost – ACK, Retransmission, SACK

Cumulative ACK

ACK číslo = „Přijal jsem všechny byty PŘED tímto číslem."

Příklad: Segmenty SEQ=1000, 2000, 3000 dorazí → ACK=4000 (jeden ACK potvrdí všechny 3).

Retransmission (znovuodeslání)

RTO Timeout

Odesílatel čeká na ACK. Timeout (200 ms–1 s) → retransmit. RTO počítán z RTT. Exponential backoff: 1s → 2s → 4s → 8s… (max 64 s).

Fast Retransmit

3 duplicate ACKs (stejný ACK 3×) → okamžitě retransmit, nemusí čekat RTO! Seg 2000 ztracen, 3000+4000 dorazí → 3× ACK=2000 → retransmit 2000 ihned.

SACK (Selective Acknowledgment)

Problém cumulative ACK: Segment 2 ztracen, ale 3, 4, 5 dorazily → ACK=2 nepotvrdí 3, 4, 5 → odesílatel neví co má!

SACK řešení: Příjemce pošle ACK=2 + „Mám 3, 4, 5" → odesílatel retransmit pouze segment 2 (ne všechny). Vyjednán při handshake (TCP Options).

10

Congestion Control

Řízení přetížení sítě – TCP detekuje congestion (ztráta paketů, zvýšený RTT) a zpomalí.

Fáze Congestion Control
1
Slow Start
Congestion Window (cwnd) začíná na 1 MSS. Každý ACK → cwnd se zdvojnásobí (exponenciální růst: 1→2→4→8→16…). Dokud nedosáhne ssthresh (slow start threshold).
2
Congestion Avoidance
Po dosažení ssthresh: cwnd roste lineárně (+1 MSS per RTT). Opatrné zvyšování → detekce limitu sítě.
3
Detekce ztráty (congestion)
Timeout: ssthresh = cwnd/2, cwnd = 1 MSS → zpět na Slow Start. 3 dup ACK (Fast Recovery): ssthresh = cwnd/2, cwnd = ssthresh → Congestion Avoidance (mírnější).
Efektivní okno

Odesílatel posílá minimum z: Receiver Window (flow control) a Congestion Window (congestion control). Effective Window = min(rwnd, cwnd).

Moderní TCP varianty
  • TCP Reno – klasický, Fast Retransmit + Fast Recovery
  • TCP Cubic – default v Linuxu, agresivnější růst cwnd (cubic function)
  • TCP BBR (Google) – model-based, měří bandwidth a RTT → optimální rate

UDP – přehled a header

Klíčové vlastnosti UDP
  • Connectionless – žádný handshake, data odesílána okamžitě
  • Unreliable – žádné ACK, žádné retransmission → ztracené pakety neobnoveny
  • Unordered – datagramy mohou dorazit v jiném pořadí
  • No flow/congestion control – žádné sliding window
  • Message-oriented – datagramy (ne byte stream jako TCP)
  • Minimální overhead – header pouze 8 B (vs TCP 20+ B)

Použití: DNS, DHCP, VoIP (RTP), streaming, gaming, SNMP, TFTP, NTP.

UDP Header (8 B)

16 b

16 b

16 b

  • Destination Port – port příjemce
  • Length – délka celého datagramu (header + data, min 8 B)
  • Checksum – error detection (volitelný v IPv4, povinný v IPv6)
Overhead porovnání

Pro DNS dotaz (50 B data): UDP overhead = 8 B (14 %). TCP overhead = 20 B (29 %) + 3-way handshake (3 pakety navíc!). UDP je 2× efektivnější pro malé zprávy.

Kdy použít co?

TCP když:

Data musí dorazit kompletní a bez chyb. Pořadí kritické. Latence není kritická (web, email, soubory).

UDP když:

Nízká latence kritická (VoIP, gaming). Ztráta pár packetů OK (video glitch > freeze). Malé zprávy (DNS). Broadcast/Multicast.

13

RTP a RTCP (bonus)

Otázka zmiňuje RTP/RTCP – protokoly pro real-time přenos médií nad UDP.

RTP (Real-time Transport Protocol)

Přenos audio/video dat v reálném čase. Běží nad UDP (nízká latence). Přidává: sequence numbers (pořadí), timestamps (synchronizace), payload type (kodek). Není spolehlivý – žádné retransmission (ztracený frame = přeskočený). Použití: VoIP (SIP + RTP), video konference, IPTV.

RTCP (RTP Control Protocol)

Companion protokol pro RTP. Monitoruje kvalitu přenosu: packet loss, jitter, RTT. Sender Reports (SR) a Receiver Reports (RR) → feedback o kvalitě. Umožňuje adaptivní bitrate (pokud špatná kvalita → sníží rozlišení).

Proč RTP nad UDP (ne TCP)?

TCP retransmission by způsobil zpoždění (čekání na ztracený packet) → u VoIP/videa horší než přeskočení framu. UDP + RTP = rychlý přenos s timestampy pro synchronizaci, bez čekání na retransmit.

14

Shrnutí klíčových bodů

Na zkoušku si zapamatuj

PŘEPÍNÁNÍ

  • Circuit switching = pevná cesta, rezervovaný BW (telefonie). Packet switching = datagramy nezávisle, sdílený BW (Internet)
  • TCP/IP = packet switching. IP nespolehlivý → TCP přidává spolehlivost

TCP

  • Connection-oriented: 3-way handshake (SYN → SYN-ACK → ACK), 4-way termination (FIN → ACK → FIN → ACK)
  • Reliable: Cumulative ACK, retransmission (RTO timeout, Fast Retransmit po 3 duplicate ACKs), SACK
  • Flow control: Sliding Window (plovoucí okno). Window=0 → stop. Window Scale → až 1 GB
  • Congestion control: Slow Start (exponenciální) → Congestion Avoidance (lineární). Effective = min(rwnd, cwnd)
  • MSS = 1460 B (MTU 1500 − IP 20 − TCP 20). Header 20–60 B
  • Flags: SYN, ACK, FIN, RST, PSH, URG
  • Použití: HTTP, HTTPS, FTP, SSH, SMTP, POP3, IMAP

UDP

  • Connectionless, unreliable: žádný handshake, žádné ACK/retransmission
  • Header 8 B (Source Port, Dest Port, Length, Checksum)
  • Podporuje broadcast/multicast (TCP ne!)
  • Použití: DNS, DHCP, VoIP (RTP), streaming, gaming, NTP, SNMP, TFTP

PORTY A RTP

  • Porty: Well-known 0–1023 (HTTP 80, HTTPS 443, SSH 22). Registered 1024–49151. Dynamic 49152–65535
  • Socket = IP:Port. TCP spojení = 4-tuple (src IP + src port + dst IP + dst port)
  • RTP = real-time media nad UDP (sequence #, timestamps). RTCP = monitoring kvality (packet loss, jitter)
  • TCP pro přesnost (web, soubory). UDP pro rychlost (VoIP, DNS, gaming)
